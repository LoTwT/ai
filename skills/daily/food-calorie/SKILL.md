# 食物热量估算与记录

## 读取必要资料

- 执行任何估算或重算前，完整读取 [references/estimation-method.md](references/estimation-method.md) 和 [references/food-calorie-index.md](references/food-calorie-index.md)。
- 创建、读取、纠正或物化饮食记录前，完整读取 [references/record-schema.md](references/record-schema.md)。
- 仅在用户明确要求生成汇总图时运行 `scripts/generate_summary.py`。

## 路由意图

先把请求归入一个模式；不要因为识别到餐次词以外的普通食物描述而默认记录。

| 模式 | 典型意图 | 状态行为 |
|---|---|---|
| `estimate` | 询问本次食物热量 | 只估算，不记录 |
| `record` | 明确记录、打卡或说明“这是我的早餐/午餐/晚餐” | 更新当前对话状态 |
| `correct` | 修改刚才或既有条目的食物、份量、做法、糖度或加料 | 覆盖目标条目 |
| `status` | 查询某日或当前累计 | 只读取状态 |
| `summary` | 明确要求汇总、出图或生成长图 | 物化 JSON 并出图 |

遵守以下边界：

1. 只要求估算时，不要声称“已记录”。
2. 未明确要求汇总时，不要自动生成图片。
3. 没有可用记录时，不要生成空汇总。
4. 不要把营养诊断、减肥处方、宏量营养素追踪或跨对话持久化扩展进本流程。

## 维护对话内状态

只在当前对话中维护每日记录，不在 `record`、`correct` 或 `status` 阶段创建每日 JSON 文件或数据库记录。按以下逻辑层级维护：

```text
daily_records[date]
  -> meals[]
     -> meal.id
     -> meal.meal_type
     -> meal.items[]
     -> meal.images[]
```

首次记录时为餐次和食物生成稳定的 `meal.id` 与 `item.id`。在本对话内保持 ID 不变；用 ID 定位纠正对象并防止重复追加。只在 `summary` 模式下把目标日期的状态物化为 JSON。

同一日期和 `meal_type` 的后续内容若明显是上一餐的补充，复用已有 meal 并追加 item，不要生成第二个 meal。只有用户明确表示这是另一次同类餐次（例如“第二次加餐”或“另一顿午餐”）时才新建 meal 和 ID；无法判断时先确认。

## 执行主流程

### 1. 归一化输入

1. 接收一张或多张图片，也接受纯文字描述。
2. 优先使用用户明确指定的日期；否则使用当前本地日期，格式为 `YYYY-MM-DD`。
3. 优先使用用户明确指定的餐次；否则结合当前对话与本地时间推断。
4. 判断多张图片是同一组食物的不同角度，还是不同食物或餐次。
5. 对同一组食物只计一次；用其他角度补充识别依据。
6. 记录实际可访问的图片路径，不要硬编码工作目录。

### 2. 识别并估算

严格执行 `references/estimation-method.md`：

1. 先识别品牌、包装文字、容量和营养标签，再扫描主食、蛋白质、蔬菜、汤、饮品、零食与明确可见的蘸料。
2. 为每项确定食物名称、烹饪方式、识别依据与置信度。
3. 合并询问所有高影响不确定项，避免连续零散追问。
4. 先量化份量，再计算热量；固体用 g，饮品用 ml，可数食物可用 piece。固定 SKU 只有在权威数量确为份数且没有更合适的 g/ml 表示时才用 serving；已知容量的饮品仍用 ml，即使其热量依据是 kcal/serving。
5. 按个人索引、包装标签、品牌官方、可靠成品数据、训练知识、Web、原料拆解的优先级取得热量依据。
6. 按食物类型选择成品、整份 SKU、复合菜、汤、饮品或蘸料分支。
7. 校验单位、算术、跨餐一致性、单项与单餐合理性，并排除重复计数和重复用油。
8. 把最终热量取为约 5 或 10 kcal 的整数展示值；后续 totals 只对这些已存储的 `item.calories` 求和。

统一使用以下冲突规则：

- 肉类主要品种不确定时必须问。
- 炒、煎、炸等做法无法区分时必须问。
- 珍珠、奶盖等高热量加料不确定时必须问。
- 份量误差可能超过 30% 时必须问。
- 糖度未知时不要问，按全糖计算。
- 杯型未知时不要问，按大杯计算。
- 蔬菜品种和调味差异影响小时不要问，采用同类合理高值。
- 成品热量数据不要再施加烹饪修正；原料拆解的整道菜只施加一次修正。

### 3. 回显结果

简洁展示每项的名称、数量、单位和热量，再展示本餐合计。只为低置信度项补充简短说明。首次记录时提醒一次照片估算存在正常误差，后续不要反复强调。

在 `record` 模式下同时展示餐次与当日累计；在 `estimate` 模式下只展示本次估算。

### 4. 更新或读取状态

按模式执行：

- `estimate`：不要更新 `daily_records`。
- `record`：把本次结果写入正确日期和餐次；同一食物的多角度照片不要生成重复 item。
- `status`：从状态中求和并回显，不要物化 JSON。
- `correct`：定位并覆盖原 item，不要追加一个“修正版”副本。

定位纠正对象时依次使用：

1. 用户明确指定的日期、餐次、序号或最近一次回显位置；
2. 对应的稳定 `item.id`；
3. 指定范围内的唯一候选。

若仍有多个候选，先请求用户确认。不要仅凭同名食物猜测；同一天出现两个同名条目时尤其如此。

按纠正类型处理：

- 修改食物种类：重新查询热量依据并重算。
- 修改份量：保持原能量密度，按新份量缩放。
- 修改做法、糖度或加料：重新进入对应计算分支。

覆盖后重新计算餐次和全天 totals。把之前生成的汇总视为过期，只有用户再次请求时才重新生成。

### 5. 更新个人索引

只把可复用且来源可靠的能量密度或明确品牌 SKU 更新到 `references/food-calorie-index.md`：

- 接受包装营养标签、品牌官方数据和来源可靠的成品数据。
- 标明来源；同一标准化键只更新一条。
- 不要写入本次照片中的份量。
- 不要把低置信度照片推断或原料拆解结果自动升级为永久基准。
- 索引文件只读或写入失败时，继续完成本次估算；不要声称数据已经保存。

## 生成每日汇总

仅在 `summary` 模式下执行：

1. 选择用户要求的日期；未指定时使用当前本地日期。
2. 按 `references/record-schema.md` 校验状态并物化 `schema_version: "2.0"` JSON；始终保留全部旧必需字段。
3. 保持 meal、item 与图片的原始顺序，并把图片路径放在对应 meal 的 `images` 中。
4. 把 JSON 写入临时文件，再运行：

```bash
python <skill目录>/scripts/generate_summary.py \
  --data <临时JSON路径> \
  --output <可访问的输出路径>/daily_summary.png
```

5. 把生成的图片交给用户。

脚本依赖 Pillow。缺少依赖时，明确提示用户安装；不要自动安装，不要使用 `--break-system-packages`，也不要修改系统 Python。
